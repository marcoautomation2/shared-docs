Manual-then-auto GUI test harness

Overnight task on linux3, 2026-09-13/14: explaining how agentTools actually drives the desktop, then building the "drive by hand once, replay by script forever" workflow for 3 of the 9 Fearless Manager GUI tests.

The setup/granularity question

The task that triggered this asked a very concrete question: what actually drives the mouse, and at what granularity does an agent make decisions versus a program just executing steps? Reading Controllers/src/agentTools/Pilot.java on this checkout (branch3, reset to upstream FearlessLang/Controllers) and comparing it against the previously-published guide at marcoautomation2.github.io/Controllers answers it, with one caveat surfaced along the way.

The mechanism. Pilot is a thin wrapper over java.awt.Robot: it moves a real pointer, presses and releases real mouse buttons and key codes, and takes full-screen screenshots via Robot.createScreenCapture. There is no separate "agent decision" process involved in any single call — glide, click, drag, chord and shot are all synchronous Java method calls that return once the OS has processed the input event. The published guide describes a richer design (a Desk interface with two backends, Awt and a Mutter one that drives GNOME's org.gnome.Mutter.RemoteDesktop/ScreenCast D-Bus session instead of X11 Robot input) plus a Pilot.type method for arbitrary text. That richer version exists only on the fork branch marcoautomation2/Controllers@agenttools-typing-guide and was never merged upstream: the code actually checked into FearlessLang/Controllers, and therefore into every fearlessBranch* working copy on this machine, is the plain Robot-only Pilot shown above, with no Desk/Mutter abstraction and no type. This machine's own gui_gym.txt describes the Mutter mechanism as if it is what Pilot currently does, which is the one genuinely stale piece of documentation behind the original confusion — worth a housekeeping pass separate from this task.

The granularity. Nothing requires a fresh model decision per Pilot call. A whole sequence of clicks, drags and key chords can be, and in this task was, written out as one deterministic Java method and run start to finish with no LLM in the loop — that is exactly what "auto mode" below is. What does need a decision each time is where things are: window placement is the window manager's, not the caller's, so the coordinates a script plays back have to come from somewhere. The two ways to get them are (a) an agent looking at a screenshot once, deciding the next click, and recording the pixel position it used — "manual mode" — or (b) Pilot.changed, which finds the bounding box of what changed between two screenshots (e.g. radius 6 to find a newly-opened window's edges while ignoring incidental redraws), letting a script locate a window without hard-coding its position. This task's scripts use recorded fixed coordinates (approach a), which is simpler but ties a script to one screen layout; a natural next step for any of them would be to swap in Pilot.changed lookups for the couple of coordinates that are layout-sensitive (the project tiles).

What was built

Of the 9 tests in fearlessManagerAutomatedGuiTests/allTests.txt, 3 were taken through the full manual-then-auto pipeline: TEST 3 (Compile and run), TEST 5 (Running program and Terminate) and TEST 9 (Recompile after Clear cache). TEST 1 (file association) and TEST 6 (window close vs Quit) were deliberately skipped: a prior overnight run on this same machine (overnightLogs/2026-09-13-full-test-run/log.md) found a real product bug in TEST 1 (the file-manager icon is installed under a hicolor directory name — the source PNG's raw pixel size — that the icon theme's index.theme never declares, so it never renders) and a desktop-focus/window-remapping quirk in TEST 6 specific to this synthetic remote-controlled desktop. Automating either now would produce a script that fails for reasons that have nothing to do with whether the harness itself works.

The workflow, concretely

  1. Manual mode. Launched the built Fearless Manager app image, then drove it click by click with a small scratch Pilot-backed CLI, deciding each next action from a screenshot. Every click's pixel position, every wait, and what was checked at each step (both visually and against the manager's own on-disk state) was logged as JSON.
  2. Auto mode. For each test, wrote one single-file Java program — same no-separate-compile-step style as Coordinator/Build/src/scripts/*.java — that replays the exact recorded clicks through Pilot, then verifies the outcome. The Fearless Manager turned out to persist rich per-project state on disk (fearless0_001/eclipse/<project>/state.txt, a small JSON blob with needsCompiling, running, runs, exit, mains, and console.txt, the exact text the output pane shows), so every check in all 3 scripts reads those files instead of taking a screenshot and reasoning about pixels — no vision needed at verification time at all.
  3. Run twice. Each of the 3 programs was executed twice back to back on the real desktop. All 6 runs passed. No leaked child process or window was left behind by either TEST 5 run (its subject app never exits on its own; Terminate is the entire point of the test).

Brittleness, honestly

  • Fixed pixel coordinates. Every click point (project tiles, the Compile/Run/Terminate button that changes label and width but keeps the same top-left anchor, the Project and Running menus and their items) is a literal number recorded once on this machine's current screen resolution and window layout. A different screen size, a maximized-vs-not window, or a third project tile shifting the grid would all silently break these scripts — they would click the wrong thing rather than fail cleanly.
  • Tile position depends on how many/which projects are registered. Tiles are laid out alphabetically; these scripts assume exactly gui_basics and hello_world are registered, in that left-to-right order. This is why "Add folder" was deliberately left out of scope for now (see below), not because it can't be scripted at all.
  • Timing. Compiles and runs of these tiny fixture projects are consistently fast (under a couple of seconds) in this environment, so generous fixed timeouts (5–15s) were enough in all 6 runs with no retries needed. A slower machine or a bigger fixture project would need larger timeouts, not a different design.
  • What is deliberately not automated. The "Add a Fearless project folder" file-chooser dialog: a prior session found that typing an absolute path into it and pressing Enter/Open silently does nothing, and the only reliable way to add a folder is to navigate the list view visually. That is exactly the kind of step that still needs a human-shaped (agent-shaped) decision per click, so these 3 scripts instead assume the two fixture projects are already registered, which they are on this machine from the prior manual run.

The intended failure-triage workflow

These auto-mode scripts are expected to go stale over time (a UI tweak, a resolution change, a new project tile) — that is an accepted tradeoff, not a flaw, because regenerating one is cheap. The workflow going forward, entirely agent-driven, no human required:

  1. An auto-mode script fails (assertion error, timeout, or a click landing on the wrong control).
  2. An agent re-runs the same test in manual mode: launch the app, screenshot, decide each click again from what is actually on screen right now, log the new coordinates and observations exactly as this task did.
  3. Compare: if the manual run's *outcome* (the state.txt/console.txt content, the actual application behavior) matches what the old auto-mode script expected, only the coordinates or timing drifted — regenerate the auto-mode script from the new manual log. That is brittleness, not a bug.
  4. If the manual run's outcome itself differs from what allTests.txt or the previous manual log says should happen, that is a real regression worth reporting, independent of any auto-mode script.
