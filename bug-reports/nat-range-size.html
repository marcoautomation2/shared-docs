Bug report: Nat inclusive-range .size is computed backwards

FearlessLang/StandardLibrary — found while reading the full Frontend, Coordinator, StandardLibrary and Commons source overnight. Published 2026-09-03, fixed upstream shortly after.

Fixed

Fixed upstream in b55cda5: .size now computes endInclusive - startInclusive + 1, the formula this report's "why this is a bug" section below predicted. The rest of this page is the original report, left as published.

What the code does

StandardLibrary/base/datatypes/numbers/nat.fear:295, inside the factory that backs every Nat range literal (~~, ~~=, =~~, =~~=): 

_NatRanges: Sealed {
  #(startInclusive: Nat, endInclusive: Nat, str: Str): Range[Nat] -> {'self
    .size -> startInclusive - endInclusive; // Performance cost is low enough that this is okay
    .start -> startInclusive;
    .end -> endInclusive;
    ...
  }

Nat.- is documented and implemented as a checked subtraction — it throws on underflow rather than wrapping (nat.fear:19-22: “returns the checked difference of this and x. Throws on underflow below 0”). Every range constructed by the four operators has startInclusive <= endInclusive by construction (each operator explicitly rejects the empty-range case before calling _NatRanges#). So for any range with two or more elements, startInclusive < endInclusive, and startInclusive - endInclusive is exactly the underflow case that throws.

Range[N].isEmpty (range.fear:25) is defined as this.size == 0, so it inherits the same failure for every Nat range.

Demonstration

Added to StandardLibrary/integrationTests/testingStandardLibrary/_test/test_nat.fear (wired into the existing TestNat suite, run the same way as every other .fear-level unit test in that project) and run against a from-source build of Commons + Frontend + Coordinator, all reset to upstream main: 

NatRangeSizeTests: Test {::
  .check{(1=~~=4).size .assertEq 4}
  .check{(1=~~=1).size .assertEq 1}
  .check{(1=~~=4).isEmpty .assertFalse}
  }

All three checks fail today:

Test failure NatRangeSizeTests at line: 96 ... {msg: "Assertion failure." | "Expected: 1" | "Actual: 0", ...}
Test failure NatRangeSizeTests at line: 97 ... {msg: "Nat -: underflow", ...}
  • (1=~~=4).size — a 4-element range — throws instead of returning 4.
  • (1=~~=1).size — a 1-element range, the one case that does not underflow (1-1=0) — silently returns 0 instead of 1.
  • (1=~~=4).isEmpty throws instead of returning False, because it calls the broken .size.

No existing test in test_nat.fear’s NatRangeTests calls .size or .isEmpty on a Nat range — the existing coverage only exercises .list/.flow, which go through _NumFlow.nats, a separate (and correct) code path. That is why this has not been caught before.

Why this is a bug

Argument for
  • An inclusive range [a, b] of a discrete type has b - a + 1 elements when a <= b. The code computes a - b: neither the sign nor the missing +1 match that formula.
  • The doc comment on Range[N].size (range.fear:19-20) says plainly: “this.size returns the number of elements in this range.” For every constructible multi-element Nat range, it instead throws.
  • Every other range-backing type in the same file family gets this right by construction — e.g. ClosedNumRange.clamp a few lines below reasons correctly about start/end ordering; only this one arithmetic expression is inverted.
  • The trailing comment — “Performance cost is low enough that this is okay” — is clearly about choosing to recompute .size on every call instead of caching it at construction time, not about the formula being approximate. The formula itself was presumably meant to be endInclusive - startInclusive + 1 (or the code could reuse .getSucc/.getPred as the range constructors themselves do).
  • This is not a narrow edge case: it fires for every Nat range of two or more elements, which is the overwhelmingly common case in real use (a single-element range is the edge case, and even that one returns the wrong answer, 0 instead of 1).

Steelmanning the other side

Argument against
  • Range[N] is a fairly young, sparsely-used corner of the standard library — NumRange (the Num analogue a few lines above) does not even implement .size at all, only .contains. It is plausible _NatRanges.size was written early, before its contract was fully settled, and simply never got a caller that would have exposed it.
  • The design deliberately routes iteration through .flow/.list (backed by _NumFlow.nats), not through .size; if .size is treated as a rarely-needed convenience rather than a core operation, a latent defect in it is a smaller deal than a defect in the iteration path itself, which is exercised (and correct) in NatRangeTests.
  • One could argue the expression was a deliberate, if confusingly named, choice to expose the signed gap start - end for some internal or future use, with the intention of taking .abs or similar at the call site — i.e. that .size here is mid-refactor rather than simply wrong. Nothing in the visible code supports that reading, but it cannot be excluded from the diff alone.
  • Because Nat.- throws loudly on underflow rather than returning a nonsensical huge wrapped value, the failure mode is at least “fail fast” rather than a silent corruption — consistent with this codebase’s stated offensive-programming philosophy, which treats a loud throw as more acceptable than most other kinds of bugs.

On balance the steelman explains how this could have shipped unnoticed, not why the formula is defensible: .size is a public, documented method on a public type, and no reading of “number of elements in this range” produces startInclusive - endInclusive.
