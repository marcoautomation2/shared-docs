Bug report: MetaParser.parseBack mixed absolute and relative token indices

FearlessLang/Commons — found while reading the full Frontend and Commons source overnight. A fix and regression test were proposed; both pull requests were closed without merging. Published 2026-09-07, corrected 2026-09-07.

What the code does

Commons/src/metaParser/MetaParser.java defines parseFront and parseBack as a matched pair: both split a token window into a kept part and a remainder, using a probe to find where. parseFront works from the start of the window and only ever reads the probe sub-parser's own index() — a count of tokens consumed, independent of where the window sits inside the full token list — then advances the caller's this.index by that same count.

parseBack is meant to be the mirror image, working from the end of the window via the sub-parser's limit() instead. But three places in it read the caller's this.limit field directly, instead of the sub-parser-relative start value it had just captured: 

var lastS= splitterParser.spanAround(end + drop, limit - 1);
Parser firstParser= make(lastS,List.copyOf(slice.subList(end + drop, limit)));
var res= firstParser.parseAll(frameName, first);
this.limit += end;//mark the tokens as eaten

this.limit only equals the sub-window's own size when the caller's index happens to be 0 — i.e. when nothing has been consumed from the front yet before calling parseBack. Whenever it isn't (an entirely ordinary mid-parse state), slice.subList(end + drop, limit) asks a list for a range that runs past its own size and throws IndexOutOfBoundsException. Even at index == 0, the final line still sets this.limit to oldLimit + end instead of shrinking it to reflect the tokens consumed from the back, leaving the parser's cursor past the end of its own token list.

Demonstration

parseBack has no callers anywhere in Frontend, Coordinator, StandardLibrary or Commons today, and Commons has no test source tree of its own (no JUnit wiring at all), so the regression test lives in Frontend’s existing FearlessFrontend/test/fearlessParser/MiscTests.java, using fearlessParser.Parser — the only concrete instantiation of MetaParser in the codebase: 

var p= new Parser(span, new Names(List.of(),List.of(),List.of()), List.of(a,b,c,d,e,f), new FearlessErrFactory());
p.expectAny(""); p.expectAny("");//front already consumed a,b: active window is now c,d,e,f
var res= p.parseBack("back", false,
  pp->{ pp.expectAnyLast(""); pp.expectAnyLast(""); return 0; },
  pp->{ var out= new ArrayList<String>(); while(!pp.end()){ out.add(pp.expectAny("").content()); } return out; });
assertEquals(List.of("e","f"), res.get());
assertEquals(2, p.index());
assertEquals(4, p.limit());

Against the pre-fix code, this fails immediately:

java.lang.AssertionError:
   metaParser.MetaParser.spanAround(MetaParser.java:165)
   metaParser.MetaParser.parseBack(MetaParser.java:301)

because spanAround is asked for an index one past the end of a 4-token slice.

Why this is a bug

Argument for
  • parseFront, the sibling method with an identical contract mirrored the other direction, never touches the caller's absolute fields for its internal bookkeeping — only deltas. parseBack deviates from that pattern in exactly the three places that matter.
  • The two methods' doc comments are otherwise identical (down to the wording), except parseBack's still says "Parses a (non empty) list of tokens from the start of this parser" — unchanged from the copy-paste of parseFront's comment, even though parseBack is supposed to parse from the end. That mismatch is itself evidence the method was never exercised after being adapted.
  • The failure is not a hypothetical extreme input: it reproduces with a plain 6-token list and the most ordinary possible calling pattern (two tokens already consumed from the front before splitting from the back).

Steelmanning the other side

Argument against
  • parseBack has no callers anywhere in Frontend, Coordinator, StandardLibrary or Commons today — it cannot actually misbehave in any code path that currently runs. A maintainer could reasonably prefer deleting the unused method over patching it.

Proposed fix (not merged)

Use the sub-parser-relative start (its own window size, captured before probing) everywhere the code previously read the outer this.limit, and shrink the outer limit to index + end — the mirror of how parseFront advances this.index by its own end. 

var lastS= splitterParser.spanAround(end + drop, start - 1);
Parser firstParser= make(lastS,List.copyOf(slice.subList(end + drop, start)));
var res= firstParser.parseAll(frameName, first);
this.limit= index + end;//mark the tokens as eaten
