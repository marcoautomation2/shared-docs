Bug report: an empty List’s .subList(start,end) uses && where it needs ||

FearlessLang/StandardLibrary — found while reading the full Frontend, Coordinator, StandardLibrary and Commons source overnight. Published 2026-09-04, fixed upstream shortly after.

Fixed

Fixed upstream in b55cda5: the guard now reads start!=0 || {end!=0}. The rest of this page is the original report, left as published.

What the code does

StandardLibrary/base/datatypes/collections/lists/list.fear:26–28, inside List[E] — the object literal that supplies the default (empty-list) implementation of every List method, the case actually reached whenever a receiver is the empty list (e.g. the literal List[Str] used throughout the test suite, or any List[E] instance that has not gained an element): 

.subList(start,end) -> Block#
    .if{start!=0 && {end!=0}} .error{`.subList(`+start+`, `+end+`) called on empty list`}
    .return {{}};

The declared contract, a few lines below in the same file (list.fear:115–116), is: “slice [start,end); throws if start>end or end>size.” For the empty list, size is 0, so the only in-contract call is .subList(0,0) — anything else should throw.

Bool.&& short-circuits (bools.fear: False.&& b -> this; never evaluates b). So whenever start == 0, the left side of start!=0 && {end!=0} is False, the whole condition is False without ever inspecting end, no error fires, and the method falls through to .return {{}} — regardless of how large end is. A call like List[Str].subList(0, 999) silently returns the empty list instead of throwing for end > size.

The condition is an inverted De Morgan: to reject anything other than (0,0), the guard needs to fire when either coordinate is nonzero (start!=0 || end!=0), not only when both are.

Demonstration

Added to StandardLibrary/integrationTests/testingStandardLibrary/_test/test_literal_errors.fear, in the existing ThrowListTests suite that already exercises every other empty-List error path (.get, .without, .withAlso, …), and run the same way as every other .fear-level unit test in that project, against a from-source build of Commons + Frontend + Coordinator, all reset to upstream main: 

ThrowListTests: Test {::
  ...
  .checkDetErr({i -> True}, {List[Str].withAlso(1,`x`)})
  .checkDetErr({i -> True}, {List[Str].subList(0,3)})
  ...
  }

The check fails today:

Test failure TestCap at line: 100 in file: testing.fear {msg: "Expected error but got success", ...}

That message is checkDetErr’s own failure branch (testing.fear:101: .ok _ -> Error.msg "Expected error but got success";) — i.e. List[Str].subList(0,3) returned successfully instead of throwing, exactly as the code walkthrough above predicts. No other test in the suite failed, confirming this is an isolated, newly-exposed defect and not a build problem.

No existing test calls .subList on an empty list with exactly one of the two arguments nonzero: the single-argument overload (list.fear:30: .subList(start)->this.subList(start,this.size)) always supplies this.size as end, which is 0 for an empty list, so both arguments happen to be 0 together in every existing call — that is why this was never caught.

Why this is a bug

Argument for
  • The documented contract on _List.subList(start,end) is unconditional: “throws if start>end or end>size.” For the empty list (size==0), .subList(0,3) has end>size and must throw; instead it returns {}.
  • The bug is silent, not loud: unlike a checked-arithmetic underflow, this path returns a plausible-looking value (an empty list) instead of erroring, so a caller that passes a bad end on an empty list gets no signal anything went wrong.
  • Every sibling method in the same literal (.get, .with, .without, .withAlso) correctly rejects any out-of-range index on the empty list unconditionally; .subList is the only one of the group whose guard only half-fires.
  • The fix is a one-character change (&& → ||), which is itself evidence this is a slip rather than an intentional relaxation — there is no plausible reading of the contract under which only jointly-nonzero coordinates should be rejected.

Steelmanning the other side

Argument against
  • The two-argument .subList is very rarely called directly on a statically-known-empty receiver; almost all call sites go through the single-argument overload or through a list that has already been checked non-empty, so this defect has essentially zero blast radius in practice.
  • Silently returning {} for an over-long end on an already-empty list is, in a sense, harmless: the “wrong” answer and the “right” answer (a thrown error) both signal “you asked for something that isn’t there” to any caller that goes on to inspect the result, and neither corrupts state, since List is immutable.
  • One could argue the intent was specifically “don’t bother erroring when the caller trivially asked for the whole (empty) range starting at zero”, and the arity check was just written slightly too permissively rather than being conceptually wrong — i.e. a scope decision, not a logic bug. Nothing in the visible code or comments supports this reading, but it can’t be excluded from the diff alone.

On balance the steelman explains why this went unnoticed (low call frequency, benign-looking output), not why the guard is correct: the file's own doc comment on subList states the throw condition unconditionally, and the sibling methods in the same literal all honor it without a joint-condition escape hatch.
