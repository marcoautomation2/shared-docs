Linux tray icon: why StatusNotifierItem, not XEmbed

Controllers PR #26 replaces the manager's AWT TrayIcon with a hand-written StatusNotifierItem (SNI) D-Bus client on Linux. The question this report answers: was that necessary, or could the old icon's clicks have been fixed in place - and does the new approach risk quietly hiding the icon instead of losing its clicks?

Short answer

The click loss is a real, decade-old, upstream KDE bug in a proxy binary Fearless does not own, with no known application-side fix - the rewrite was the correct call, not scope creep. The "hidden icons" worry is legitimate as a UX note but is not a regression: the pre-PR icon already reached Plasma through the same SNI exposure with the same Status=Active value. What is still unverified is whether a click on real KDE hardware now reaches the manager - the PR says so itself.

1. The premise: does the old code get an icon onto a KDE tray?

Yes, and the mechanism matters. KDE Plasma has not spoken the legacy XEmbed systray protocol natively since the Plasma 5 era; its panel widget only understands StatusNotifierItem. A compatibility component, xembedsniproxy (part of plasma-workspace), is what lets any XEmbed app - including a Java TrayIcon - show up at all: it embeds the app's tiny XEmbed window inside an invisible container and re-announces that container to Plasma as an SNI item. So "the icon appears" on KDE already depends on this proxy; it was never native XEmbed rendering.

2. Is the click loss a known bug, and is there a simpler fix?

Read directly from KDE's own bug tracker and the proxy's current source:

  • KDE bug 355504, "xembedsniproxy: java tray icon doesn't work" (2015). A KDE developer's own comment explains the mechanism: the proxy raises its transparent container to the top, moves it under the pointer, injects one synthetic press/release pair into the embedded window, then lowers the container again - "even user clicked twice, that's 'two' single click, not 'double click'."
  • KDE bug 356500, "xembedsniproxy icons doesn't respond to clicks" (2015). A commenter reproduces it with a Java Swing app (JDownloader 2); the proxy's own debug log labels the embedded window JavaEmbeddedFrame and skips it as a "transparent xembed icon."
  • Both reports were closed as duplicates of one another and ultimately of bug 358328 ("no context menu"), with no comment in the chain describing a fix that restores click delivery for Java-created XEmbed windows.
  • Still reproducing a decade later: a KDE Discuss thread from a user on Ubuntu 24.10 / Plasma 6.6 - icon renders, a minimal TrayIcon + MouseListener program receives zero click events, thread ends unanswered.
  • Reading sniproxy.cpp directly: the click path auto-selects between a direct xcb_send_event injection and an XTest fallback, and one comment in the code notes it was specifically tuned against GTK's quirks ("GTK doesn't like send_events and double checks the mouse position matches where the window is"). No equivalent tuning for Java AWT/Swing's embedded-frame windows is documented anywhere in the file or the bug threads - consistent with those windows being the ones that get silently skipped.

No application-side workaround was found in any of these sources. The only mitigation mentioned anywhere (toggling the KWin compositor off and back on around the click) is a host-side manual step, not something a shipped application can invoke or rely on, and is not reported as reliable even then. The bug lives inside a C++ binary Fearless does not ship; there is no Java API, system property, or TrayIcon usage change that reaches into it.

3. Does SNI risk hiding the icon that XEmbed didn't?

The StatusNotifierItem spec defines a Status property: Passive ("likely that visualizations will choose to hide it"), Active (shown), NeedsAttention (emphasized). gui.Sni always reports Active.

The comparison that answers the regression question is what the old code already reports. sniproxy.cpp's own Status() method:

QString SNIProxy::Status() const
{
    return QStringLiteral("Active");
}

Unconditional, for every proxied XEmbed icon, Java's included. The pre-PR AWT tray icon was therefore already being announced to Plasma as an SNI item with Status=Active - the identical value gui.Sni sets directly. PR #26 removes the proxy layer; it does not change what Plasma is told about the icon's importance, and so does not change its exposure to whatever visibility policy Plasma applies to Active items.

That policy is real, though: KDE's own System Tray documentation describes the per-entry "Auto" visibility setting as showing an icon "only ... when the service is active" (mirroring the spec's Passive/Active split), and independent user reports - e.g. an Arch Linux forum thread titled "Plasma application tray icons always hidden on default Auto setting" - describe icons landing in the collapsed "hidden icons" chevron on first appearance regardless of nominal active status, needing a manual drag-out or a Visibility → Shown override. No KDE document was found that pins down the exact first-run placement rule (the Community wiki's NewSystemTray design page covers categories and properties, not a first-appearance algorithm) - this detail rests on consistent user testimony, not a citable spec paragraph, and is flagged as such rather than overstated.

This is a generic, protocol-agnostic Plasma behavior, and not unique to Linux: Windows 11's notification area has shipped the same pattern since its redesign - newly-installed apps' tray icons default to the hidden overflow drawer until dragged out (a widely reported annoyance for apps like Discord or Google Drive after a fresh install). It is standard tray-declutter UX in 2026, not a fault introduced by choosing SNI over XEmbed.

4. Is XEmbed a durable thing to invest in fixing?

No. KDE Plasma has needed the XEmbed-to-SNI proxy since the Plasma 5 era specifically because its panel only understands SNI now; XEmbed survives purely as a compatibility shim maintained by the KDE project, not a protocol Plasma implements natively. GNOME dropped its built-in legacy tray outright and only regained one via the AppIndicator/ubuntu-appindicators extension - itself an SNI client, and the same extension the manager already targets on GNOME. XFCE, Cinnamon and MATE speak SNI natively per the PR's own description. Even a hypothetical fix for the XEmbed click bug would only be patching a legacy compatibility path that every current desktop is moving away from, owned entirely by a project outside this one's control.

What the PR gets right, and what is still open

  • The loud-failure behavior from #23/#24/#25 (no tray, icon removed, window not shown) carries over unchanged onto the D-Bus path - good continuity with the existing violation handling.
  • The PR's own text already states the "hidden icons" caveat accurately ("Plasma may put it under the 'hidden icons' arrow the first time; you can pin it in the tray settings") - this report confirms that line is correct and not something the PR is hiding from the reader.
  • Genuinely open: nobody has yet confirmed a left click reaches the manager on real KDE/X11 hardware through gui.Sni. The PR text says so directly ("The KDE check is left to the reporter"); this machine has no KDE session available to close that gap. GNOME 50 with the appindicator extension, and an independent D-Bus client (busctl) parsing every reply, were the only things verified so far.
  • No dbusmenu on Linux yet (Menu is /NO_DBUSMENU), so there is no right-click "Show/Quit" popup - called out in the PR as a possible follow-up, not a defect of this change.

Method & confidence

PR #26 and its stack (#22-#25) were read in full through gh, including comments and reviews (both are empty - the text quoted in the task is the PR's own description). The KDE bug reports, the KDE Discuss thread, and sniproxy.cpp were read directly rather than taken from secondary summaries. The freedesktop SNI spec and KDE's own System Tray user documentation were read directly for the Status/visibility claims. The "hidden on first run" specific behavior is corroborated by multiple independent forum reports rather than a single primary source, and is presented with that caveat rather than as settled fact. No KDE desktop was available on this machine to independently reproduce either the original click loss or the new SNI behavior; both rest on the cited external reports plus the PR author's own GNOME-side testing.
