Finding — real-desktop file drag test fails reproducibly

DesktopDragTest.aFileDraggedOntoAFolderMovesInsideIt reproducible, cause narrowed

Ran twice back to back (after waiting out an unrelated build-directory lock from a concurrent script run in the same checkout), identical failure signature both times:

java.lang.AssertionError
  at agentTools.Pilot.changed(Pilot.java:95)
  at agentTools.DesktopDragTest.row(DesktopDragTest.java:51)
  at agentTools.DesktopDragTest.aFileDraggedOntoAFolderMovesInsideIt(DesktopDragTest.java:35/36)

The test opens a real Explorer folder window via Desktop.getDesktop().open(), sends an arrow key, and expects a solid changed region (the selection highlight) between before/after screenshots of that window; Pilot.changed's assert bestN>0 fails because no such region is found. Run 1 failed on the first row() call (the VK_DOWN selection), run 2 on the second (VK_UP) — different point, same assertion, both within the same freshly-opened-window step. This points at the just-opened Explorer window not reliably holding keyboard focus by the time the arrow key is sent (the fixed 400ms pause after Desktop.open() may not always be enough on this machine), rather than a Pilot mechanism failure in general — plain clicks, drags and key presses inside already-focused windows worked correctly throughout the rest of this run (see the manual GUI tests below, driven with the same input primitives). Not fixed as part of this task; the test's own cleanup (closing the Explorer window, deleting its temp folder) did not run because the assertion aborts mid-test, so this was done by hand afterward.

Finding — Compile/Run output needs scrolling to see in full

TEST 3, step 4 reproducible

The plan requires "all the text is visible, no need to scroll output to see it all, no need of manual resizing" after running all 5 mains of the hello_world project. This did not hold: the Output panel is a fixed-height text box with its own scrollbar, and after the run it auto-scrolls to the bottom, leaving the first lines (--- compiling helloWorld ---, --- compile done ---, --- running hello.Hello1 ---) scrolled out of view. Confirmed by dragging the panel's own scrollbar thumb from mid-track to the top and finding those lines still present, just not shown by default. The Manager window was already maximized to the full 1920×1080 screen at the time, so this is not a can't-resize-far-enough artifact of this particular run; it is a genuine layout limitation of the fixed-height Output panel once enough mains have run to fill it.

Notes

  • Working copy was reset to upstream main on all seven repos (align-branches) before anything else; five sibling overnight agents' PRs against Frontend, Commons, Coordinator and StandardLibrary were left open, unmerged, and untouched.
  • A build-directory race was hit twice: this task's own script runs (TestAllController.java) and a delegated sub-task's builds (TestAgentTools.java / DeployManagedFearless.java) both write to the same out/modular directory in one checkout when run concurrently, producing transient module not found javac errors with no real cause. Resolved by serializing: waiting for one side's java.exe processes to fully exit (checked via Get-Process) before starting the other. Not a product bug, an operational hazard of running two Java-script launches against the same working copy at once.
  • Controllers' agentTools.Pilot in this checkout drives input purely through java.awt.Robot (SetCursorPos/mouse_event/keybd_event equivalents). Plain clicks, key presses, and drags within already-focused application windows worked reliably throughout the whole session; the one place a fresh window's keyboard focus was not reliably ready in time was the DesktopDragTest finding above.
  • No file left behind by this task affects any repository; the built application images, scratch PowerShell helpers, and screenshots used for verification live only in the fearlessBranch3 working copy / session scratchpad, not committed anywhere.
