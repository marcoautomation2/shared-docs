Fearless test run comparison: linux vs windows

A side-by-side read of linuxresults.html (2026-09-13, linux3) and winresults.html (2026-09-14, win3), both run against marcoautomation2/fearlessBranch3 after an align-branches reset to upstream main. This page asks three questions: what fails on both systems, what fails on only one, and whether the two runs were actually exercising the same events closely enough to answer the first two questions with confidence.

One same-named test fails on both systems, but not via the same code path — one platform-specific product bug confirmed on each side — the linux report's own totals contradict its own table — the shared manual test plan is written in Windows-only terms and the two runs verified it at different levels of rigor

Nothing here required a code change. One GitHub issue was filed (linked at the bottom) about the one finding with enough cross-platform evidence to act on; everything else is reported as-is for a human to prioritize.

On that narrow slice, linux and windows really are testing the same events, and both are clean.

Open question: the two “assumption-skipped” tests

Windows reports 2 JUnit-aborted (assumption-skipped) tests — one inside TestAllFrontendCoordinator, one inside the integrationTests phase — naming neither test nor the assumption that failed; its own report says the console summary gave no further detail. Linux reports plain 0 failed on the same two suites with no mention of a skip category at all. Three explanations remain open and are not distinguishable from either report as written: the assumption is genuinely environment-gated and only trips on Windows (plausible: an OS-detection Assume); or it is timing/ordering-sensitive and could trip on either OS; or linux's own report-writer folds aborted/skipped tests into “0 failed” without surfacing them, hiding a skip that also happened there. Whoever generates these reports should have the underlying JUnit console output name the skipped test explicitly (it is available in the raw JUnit summary either way) instead of leaving this to be inferred.

2. The one test that fails on both — but not for the same reason

DesktopDragTest.aFileDraggedOntoAFolderMovesInsideIt same test name, different failure site on each OS

Both reports title this as “a reproducible desktop-drag test failure,” and it is tempting to read that as one confirmed cross-platform bug. Reading the actual assertion each one hit shows they are not the same failure:

Windows aborts inside Pilot.changed, called from DesktopDragTest.row() (Pilot.java line 95, assert bestN>0) — before the drag ever happens. The test presses an arrow key 400ms after the folder window opens and expects a visible selection-highlight change inside that window's own screenshot region; none is found. Run 1 failed on the very first arrow key (VK_DOWN); run 2 succeeded on that one but failed on the very next arrow key (VK_UP) a moment later. A window that never had focus at all would be expected to fail both arrow presses identically every run, so the evidence points more precisely at an intermittent focus/redraw race around the freshly-opened window than at a total, deterministic focus miss.

Linux does not hit that assertion at all — both row() calls and the drag() itself complete without error — and instead fails the test's own final assertion: the file is still at its original path, never having moved into destination/. So on linux the mechanics of finding and dragging the icon all appear to work; only the file-manager's actual handling of the drop does not have the intended effect (or the drop lands on the wrong target, per the linux report's own stray-window-focus hypothesis).

Net: this is one brittle test failing reproducibly on both operating systems, evidence for a real weakness in how DesktopDragTest synchronizes with a freshly-opened, OS-native file manager window before driving it — but the two runs' own evidence does not support calling it “the same bug” underneath. It could equally be two distinct flaky-focus mechanisms that happen to share a brittle test. See the filed issue at the bottom of this page.

4. Are the two runs actually testing the same events?

For the four automated JUnit suites: yes, convincingly (§1). For everything else, only partly:

  • The shared manual plan is not actually OS-neutral. manager-gui-tests.txt (draft v7), linked identically from both reports as the source of truth, is written in Windows-specific terms throughout — it names fearlessManaged0_001w.exe and “Explorer” directly, with no Linux (or OS-neutral) variant. The linux run had to silently substitute a file manager (Nautilus) and a differently-named binary for every step that mentions these, an interpretive step the windows run did not need. Test 1's whole icon-lifecycle narrative (§3) is a direct casualty of this: the plan was written around one OS's association model and the linux run is being graded against a script that does not actually describe how Linux file associations or icon themes work.
  • The two runs verified the plan's own steps at different granularity. Windows numbers every check against the plan's own step numbers (e.g. “Test 3, step 4”) and explicitly quotes the plan's “no need to scroll” requirement as the thing it tested and failed. Linux reports Test 3 as a single pass (“matched fixture output exactly”) with no step breakdown and no mention of checking the no-scroll requirement at all. Since the Output panel is shared Manager GUI code with no obvious OS-specific rendering path, the most likely explanation is not that linux is bug-free here, but that the linux run verified output *content* and never exercised the specific UI-visibility check windows did. The windows-only finding in §3 should be read as “found on windows, not checked on linux,” not “present on windows, absent on linux.”
  • Different calendar days, not a pinned commit. Linux ran 2026-09-13, windows 2026-09-14, each independently reset to whatever upstream main was at that moment via align-branches. The four suites' matching test counts (§1) are reassuring but not proof the two runs saw byte-identical source; a report that wants to make a precise cross-platform product claim should pin and record the commit hash it tested, which neither report does.
  • No shared pass/fail/skip vocabulary. Windows distinguishes failed from assumption-skipped (JUnit “aborted”); linux's tables only have pass/fail. A test that is skipped rather than run cannot be silently equated with one that passed, and right now nothing forces the two report formats to agree on that distinction (§1).

One genuine point of agreement worth calling out on its own: both runs, independently and without prompting each other, discovered the exact same undocumented step — a freshly-added project folder needs one “Become code” click before Compile appears, which the plan text does not mention. Two independent runs landing on the identical, specific gap is good evidence manager-gui-tests.txt itself is missing a step, worth folding into the next draft of the plan.

5. Report-generation defects found while comparing

linuxresults.html's own summary banner contradicts its own suite table confirmed by arithmetic

The banner reads “Automated suites: 4/4 green (1360/1360 tests)”. The table directly beneath it lists 981 + 258 + 1276 + 121 = 2636 tests across those same four green suites — not 1360. The number 1360 is exactly 981 + 258 + 121: the 1276-test integration suite's count was dropped from the banner total while the suite itself is still listed and counted as one of the “4/4 green”. Windows's equivalent banner (“2636/2636 tests”) sums its own table correctly. This looks like an arithmetic bug in whatever produced linuxresults.html's headline number, not a real discrepancy in what actually ran — the per-suite failed-count column (all zero) is internally consistent and matches windows exactly (§1) — but it means the linux report's own top-line claim should not be trusted at face value without checking the table under it.

A second, smaller instance of the same kind of slip sits in the footnote directly under the table: “TestAllFrontendCoordinatorIntegration's 1276 total is two JUnit launches inside one script: 981 (Frontend+Coordinator, same as the second row) plus 295 integrationTests.” The second row in that same table is TestAllFrontendCoordinator, whose count is 258, not 981 — 981 is the count on the first row (TestAllFrontend). Windows's parallel footnote states the same 981+295 breakdown without misattributing which row it matches.

Recommendations

  • Give the manual test plan (manager-gui-tests.txt) an OS-neutral rewrite, or an explicit linux variant, instead of leaving Windows-specific wording (.exe, “Explorer”) for each linux run to silently reinterpret.
  • Add the “Become code” click as an explicit plan step (both runs independently hit it).
  • Have future automated-suite reports name the specific test behind any assumption-skip/abort, and use a consistent pass/fail/skip vocabulary across linux and windows reports.
  • Have future reports state the exact commit hash tested, not just the calendar date, so cross-machine comparisons are against a pinned snapshot.
  • Whoever/whatever generates a report's headline summary line should compute it from the same table it sits above, not restate it by hand — see §5.
