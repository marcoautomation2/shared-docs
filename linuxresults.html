Finding — real-desktop file drag test fails reproducibly

DesktopDragTest.aFileDraggedOntoAFolderMovesInsideIt reproducible, cause unconfirmed

Ran twice back to back, identical result both times:

org.opentest4j.AssertionFailedError: expected: </tmp/desktopDragTest/destination/example.txt> but was: </tmp/desktopDragTest/example.txt>

The test opens a real folder window, locates a file icon and a destination-folder icon by screenshot diffing, then drags the file onto the folder with agentTools.Pilot.drag (press → move → release via java.awt.Robot). The file never moves: window setup and keyboard-driven row detection both succeed (so Robot key events reach the real focused window fine), but the drag itself has no effect on the file manager.

This machine's desktop is shared with three other agents' own terminal windows, and a known hazard for exactly this class of test is a stray window stealing focus or partially overlapping the freshly opened folder window mid-test, in which case a missed drop can silently land on that other window instead of the target folder. That is a plausible, though unconfirmed, explanation here — I did not have a way to capture the desktop state at the exact moment of the drop to confirm it. Recommended follow-up: re-run TestAgentTools.java alone with no other agent GUI activity in parallel, and if it still fails, capture a screenshot at drop time to see what is actually under the cursor.

Finding — Fearless-family file icon never appears (Test 1)

hello_world.fearless keeps its generic icon even after a correct registration reproducible, cause found

Test 1 needs a clean starting point (no program registered for .fearless at all), which this machine did not have — another agent's own Fearless Manager install already owned it. That registration was backed up, removed for the duration of this one test, and restored byte-for-byte afterward; xdg-mime query default application/x-fearless was used to confirm the restore before finishing.

With a genuinely clean start: opening a file manager on the project showed the expected generic icon, and running the manager did register Fearless as the default handler for .fearless correctly (xdg-mime query confirmed it, and the generated mime package XML correctly names its icon). But the file's icon in the file manager never changes to the Fearless icon — verified with a plain refresh and, separately, a fully fresh restart of the file manager process.

Root cause, found by reading source only (nothing changed or rebuilt to test a fix): LinuxAssociations.put() in Commons/src/fileAssociations/LinuxAssociations.java reads the icon PNG's own pixel width/height straight out of its header and uses that number as the icon theme's directory name (e.g. this build's 477×477 icon.png lands in ~/.local/share/icons/hicolor/477x477/mimetypes/). The system's own hicolor/index.theme only declares the standard sizes (16 up to 512 in fixed steps, plus scalable) and has no 477x477 entry, so no spec-compliant icon-theme lookup (Nautilus included) ever looks in that directory — the icon is correctly referenced by name everywhere, but physically unreachable. Any Fearless-family icon whose source PNG is not exactly one of hicolor's standard sizes will hit this.

Everything else in Test 1 checked out: the ambiguous-registration guard, the "nested folder" and "forget association" confirmation dialogs (with clear, specific wording naming both folders/paths involved), and the register/forget/re-register lifecycle all behaved correctly and matched the plan.

Smaller, separate observation: the very first manager launch against the clean baseline produced no association at all (no error, no file written), while a second identical clean-relaunch cycle worked; ProcessHandle command resolution, HOME/XDG_DATA_HOME, and target-directory writability all checked out fine in isolation, so the cause of that one intermittent miss is unconfirmed.

Finding — relaunching while the manager is already running does not bring its window back

Test 6, step 2 blocked by a stuck window, not fully confirmed as a product bug

Closing the manager's window (its own X button) correctly left the process running (confirmed via ps), matching the plan. Relaunching the same binary while that process was still alive correctly avoided starting a second process (also matching the plan), but its window did not visibly reappear or accept focus through any normal interaction; the OS-level window list showed it as still unmapped. Forcing it to map and take focus via window-management calls (not synthetic input) did reveal it with its full state intact (both registered project tiles, the earlier compile/run output log, all preserved correctly) — so the application's own state survived cleanly — but the window then stopped accepting any further clicks at all, so "Quit manager" could not be exercised through it. The process was killed directly and a fresh launch used to continue.

Later in the same session, quitting a normally-launched (never stuck) window via its own "Quit manager" menu item worked perfectly and exited the process cleanly. So the underlying capability works; only the specific "reappear after a relaunch while alive" path did not, in this synthetic, remote-controlled desktop session. Recommended follow-up: someone with a normal desktop session should check whether relaunching a single-instance Fearless Manager brings its window to the front as expected there.
