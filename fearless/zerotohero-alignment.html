ZeroToHero: build & alignment check

MarcoServetto/ZeroToHero — a browser-playable Fearless teaching game, and its companion guide. Investigated overnight 2026-09-09, against a fresh align-branch reset of Commons/Frontend/Coordinator/StandardLibrary to upstream main. Published 2026-09-09.

86 / 90 chapter tests pass 4 fail, all traced to same-day compiler commits 1 incidental fix, PR open

ZeroToHero's own playable game content builds clean and is not stale. The guide book (assetsGuide, 28 chapters) is a generated copy of FearlessTour's JUnit-backed chapters, and that copy is currently in sync with its generator. But four of those chapters currently fail to compile against the Fearless in this repo's own upstream/main tonight — not from bit-rot, but because three commits landed today change exactly the behaviour these chapters exercise. See “What's currently misaligned” below.

How the pieces fit together

Neither ZeroToHero nor FearlessTour ships a README, so this layout had to be reconstructed by reading the source and actually building it (recipe now on the setup cheatsheet). Three things were not obvious going in:

  • The playable game is a Java program, not Fearless source. ZeroToHero/src/levels/day01..day06 and htmlMangle/ are plain Java that renders the day-by-day HTML puzzle game (Walking, Gather, Climb, Archery, Forest, Fishing). The Fearless-looking code shown inside the puzzles (Direction:{.turn:Direction;} and similar) is hand-typed literal text in Java string blocks. module-info.java declares requires Coordinator;, but nothing in the repo actually imports a Coordinator class — the puzzle content is never run through the real compiler. That is the gap that lets the drift below go unnoticed: nothing here would fail loudly if it did.
  • The guide book is generated from a sibling repo, silently. ZeroToHero/src/assetsGuide/*.html (28 chapters, matching a book titled “Fearless: Zero to Hero”) is written entirely by FearlessTour/src/compileHtml/CompileHtml.java, which reads FearlessTour/src/chaptersOfZeroToHero/ZH_*.java and writes straight into ../../../ZeroToHero/src/assetsGuide — it assumes the two repos are checked out as siblings. This wiring exists only in that one source file; nothing documents it.
  • FearlessTour needs Coordinator's test source tree, not the shipped module. FearlessTour's own TourHelper/CompileHtml import mainCoordinator.ResolveResource, a machine-local test helper that lives under Coordinator/test/ (with a gitignored LocalResources.java copied from a template), not under the production Coordinator/srcModule that ships in the portable/manager builds.

What's currently misaligned

FearlessTour's 90 chapter tests (chaptersOfZeroToHero, run via TourHelper.run(), which compiles the embedded Fearless code through the real mainCoordinator.ProgrammaticMain) were run against tonight's freshly-aligned Frontend/Coordinator/StandardLibrary. 86 pass. 4 fail, and each traces cleanly to a Frontend or Coordinator commit dated 2026-09-08 — today, or the day before this ran. Because the guide-generation pipeline above is confirmed in sync (regenerating assetsGuide from current FearlessTour reproduces the checked-in files byte for byte), these same four chapters are exactly what a reader of the published guide sees right now.

1. Chapter 24 “Collections” — nested generic capability now correctly enforced

TestZH_024Chapter03Collections.tests()
Guide pageassetsGuide/24_01.html
LandedFrontend@3cd43de, 2026-09-08 15:47, Frontend#38 + StandardLibrary#49 — already logged as type-system bug #2.

Before this fix, eqModVar discarded the capability of a generic argument at depth 1, so e.g. mut Box[mut Cell] <: mut Box[imm Cell] held in both directions — unsound. Fixed, it is correctly invariant. The chapter's TestOrderByAndFlows example calls OrderBy[Person,Nat].view(_) with an argument whose inferred type is iso F[read Car,Person], which the method signature requires as F[read Car,read Person] — exactly the shape the old bug used to wave through: 

While inspecting "#(_)" line 264
This call to method "OrderBy[Person,Nat].view(_)" can not typecheck.
Argument 1 has type "iso F[read Car,Person]".
That is not a subtype of "F[read Car,read Person]" (the type required by the method signature).
Error 8 TypeError

The example needs a capability annotation added; content only Marco should choose the wording for.

2. Chapters 22 & 23 “Show Tanks” / “Show All Tanks” — a brand-new doc-comment marker collides with a divider style

TestsZH_022Chapter03ShowTanks.allCode() (5 occurrences), ZH_023Chapter03ShowAllTanks.showAllTanks1() (6 occurrences)
Guide pagesassetsGuide/22_01.html, assetsGuide/23_01.html
LandedCoordinator@22861bc “Recognize //- for test-only setup lines excluded from docs”, 2026-09-08 11:34.

Both chapters compose several conceptual “files” into one compiled string, separated for human readability with //File name.fear labels (decorative only — there is no real multi-file mechanism here, it all compiles as one test/_rank_app111.fear) and a dashed divider: 

use base.WidenTo as WidenTo;
//----------------------------------
//File _tank_game/point.fear
Points:{#(x: Nat, y: Nat): Point -> Point: ToStr{ 'self
  ...

//---------------------------------- starts with the literal three characters //-. The new doc scanner (SourceDocs.java) checks ///, then //>, then //-, in that order, before falling through to a plain // comment — so every divider line is now swallowed as a //- “test-only doc line” instead of an ordinary comment, which breaks doc-comment attachment tracking: 

While inspecting the documentation of package test
This documentation is attached to nothing.
A /// or //> block documents the declaration right below it, and nothing else
may come between them. A line starting with // ends the block, so check whether
one of these was meant to start with /// instead.

This is a plain syntax collision, not a defect in either side's stated design: the //- feature's own commit describes it as being for short setup snippets like .let x = {1}, not decorative dividers, and the guide's divider style predates that feature by definition. Whether the fix belongs in the scanner (require a fourth character not -?) or in the guide (stop using a dash divider that happens to start with //-) is a call for whoever owns each side.

3. Chapter 17 “ImplementingFromScratch” — crashes the compiler; possibly a new, uncatalogued case of an already-tracked StandardLibrary bug class

TestZH_017Chapter03ImplementingFromScratch.var1()
Guide pageassetsGuide/17_01.html
LandedCoordinator@c811ce3 “Fail the build when a hand-written rt/ class shadows a real Fearless method body”, 2026-09-08 16:30, Coordinator#101.

This lands a corrected MagicConsistency.checkFileReplacement: it now catches a StandardLibrary type where a hand-written rt/*.java file fully replaces a generated class that still has a real (non-abstract, non-Magic!) method of its own — the same failure shape as the Int.wrapIndex bug this check exists to catch. Its own commit message reports 12 pre-existing instances found this way against current upstream StandardLibrary (9 dead-code shadows, 2 unfulfilled Magic! declarations, 1 file-replacement finding on InMemoryLog), explicitly scoped as StandardLibrary-side follow-up, out of scope for that PR. (Two of those — IsoPods/FilterAny — were already worked overnight before this chapter ran.)

var1() does not produce a type error — it crashes the compiler outright: 

Error: Fearless crashed (this is a bug).
java.lang.AssertionError: Vars$o$0 is fully replaced by a hand-written rt/ file but still has a real (non-abstract, non-Magic!) method of its own
	at naiveBackend.MagicConsistency.checkFileReplacement(MagicConsistency.java:37)

Vars is not among the 12 named findings above. The teaching content itself is exactly why this chapter is called “implementing from scratch”: it deliberately defines its own top-level Vars: { #[E: imm,mut,read](var: E): mut Var[E] -> { .get -> var; } }, re-implementing (with a real body, not Magic!) the same concept the standard library's own base/var.fear provides as Vars:Sealed{#[E:*](var: E): mut Var[E] -> Magic!}, backed by a hand-written rt/Vars$o$0.java. Across all 90 chapter tests, var1() is the only one that declares its own top-level type literally named Vars. That is circumstantial, not a confirmed root cause — this write-up did not trace the backend's synthetic-name generation far enough to be certain — but it is a strong enough correlation to be worth someone checking: does a user type that happens to share a base-library type's name (and its zero-abstract-method, single-factory-method shape) get its generated <Name>$o$0 confused with the library's own, unrelated to whatever the other 12 known findings turn out to need? Flagging it rather than guessing at a fix in StandardLibrary/rt/Vars$o$0.java or in naiveBackend — that call needs more certainty than this investigation reached.

Everything else checks out

  • The playable game reproduces exactly. Rebuilding Commons, FearlessFrontend and Coordinator as real JPMS modules from tonight's upstream/main (matching how tools.PortableApp packages them, plus the flexmark jars ZeroToHero's module-info.java asks for), compiling ZeroToHero/src against them, and running mainZeroToHero.Main regenerates every file under src/assetsDest and src/assetsLeo — git status reports zero changes.
  • The guide reproduces exactly. Running FearlessTour's own compileHtml.CompileHtml against current chaptersOfZeroToHero regenerates every file under ZeroToHero/src/assetsGuide byte for byte, so the checked-in guide is not stale relative to its own generator — the four chapters above are exactly what the generator produces today, not a leftover from before some other fix.
  • 86 of the 90 chapter tests pass outright — everything in chapters 1–3 except the three listed above (directions, turning, method calls, tanks with captured state, basic promotions/packages/object capabilities), plus all of chapter 4. By inspection, the early material matches the syntax ZeroToHero's own day01–day03 puzzle levels teach.

Smaller findings

  • Fixed, PR open: ZeroToHero/.gitignore ignored both src/main/RealMain.java and src/mainZeroToHero/RealMain.java — leftover from a package rename; no src/main directory exists any more. Removed the stale line: ZeroToHero#18.
  • ZeroToHero/src/module-info.java declares requires Coordinator;, but no Java file in the repo imports anything from it. Left alone rather than removed: it reads like scaffolding for a feature that was never finished — actually validating the embedded puzzle content against the real compiler, which would have caught everything in this report automatically. Worth deciding deliberately either way, not by a drive-by deletion.
  • Neither ZeroToHero nor FearlessTour has a README. The build recipe reconstructed for this investigation is now on the setup cheatsheet so it doesn't have to be rediscovered next time.
