Fearless tests in Eclipse's JUnit view

A small, verified way to see every individual Fearless-level .check/.test — not just one bulk pass/fail per project — as real entries in Eclipse's own JUnit view, all from a single report file. Published 2026-09-06, updated the same day to accumulate into one file instead of one per project.

What already exists

StandardLibrary's unit-test facility (base/testing.fear, the UnitTests/TestCap types behind every .check and .test) already logs each individual check as a JUnit-report-shaped <testcase> element — classname, name, file, line, and, on failure, a nested <failure> with expected/actual/stack trace — through base.UnitTestLog into <project>/.out/logs/_base/unit_test_log*.log. A real line from that log, taken from a passing run of StandardLibrary's own test suite: 

<testcase classname="ByteArithTests" name="ByteArithTests at line: 2" file="_test/test_byte.fear" line="2"></testcase>

And from the one project whose job is to demonstrate a failing check: 

<testcase classname="MyTests" name="MyTests at line: 5" file="_hello/_rank_app.fear" line="5">
<failure>
<expected>3</expected>
<actual>1</actual>
Assertion failure.
...
</failure>
</testcase>

That format is exactly what Eclipse's JDT JUnit view expects — the same schema produced by Ant/Surefire/the JUnit Platform Console Launcher's --reports-dir. It just was not, until now, wired into anything a developer would actually see.

The gap

Coordinator's own Java test suite (Coordinator/test/integrationTests/RunIntegration.java) runs each Fearless integration-test project as one JUnit @Test method, e.g. testingStandardLibrary(), and only asserts that no line printed to console starts with "Test failure ". So today, running "all tests" — in Eclipse or from the command line — shows exactly one pass/fail node for the whole of StandardLibrary's suite, never the individual checks inside it (currently 1734 of them, one per .check/.test call across StandardLibrary).

What this adds

A small, test-only change to RunIntegration.java: after each Fearless project runs, find the newest unit_test_log*.log for that project, strip the internal PLAN|... planning lines (turning any PLAN|DISABLED|... line into a <testcase>...<skipped/></testcase> entry first), and wrap what is left in a <testsuite name="…" tests="…" failures="…" errors="0"> block. Every project's block accumulates — in a plain in-memory list, across the run — into one <testsuites>-wrapped file at Coordinator/.out/junit_xml/all_auto_tests.xml, rewritten each time a new project's results come in. Nothing hardcodes which projects report: whatever runs base.UnitTests lands in that same file, including a project added tomorrow. This runs as a side effect of the existing @Test methods, so it happens automatically every time "all tests" run — the console-launcher script or Eclipse's own runner, no extra step to remember.

That XML is exactly the format Eclipse's JUnit view can import as a full test-run session: open the JUnit view, click the small dropdown beside the history-clock toolbar icon, choose Import…, and pick the one file. Eclipse rebuilds the whole run as if it had just executed it — a real tree with one top-level node per project and one leaf per Fearless-level check underneath it, individually green/red/skipped, with complete failure detail for anything red.

Verified, concretely

Built and run for real, twice. First pass (the original PR #90): a fresh portable Eclipse 2026-06 ("Eclipse IDE for Java Developers", eclipse-java-2026-06-R-win32-x86_64.zip), a Java project pointed at a real Coordinator checkout, compiled clean (0 errors) under Eclipse's own compiler at language level 21, then the actual test suite run to produce real XML reports, then imported into the JUnit view by hand — one file at a time, as described below at the time.

Second pass (the accumulation change, PR #94): reused that same Eclipse install and workspace, reran the full Coordinator suite via the console-launcher script, confirmed the resulting all_auto_tests.xml parses as one well-formed <testsuites> document (4 <testsuite> blocks, 1752 <testcase>, 1 <failure>, 11 <skipped> — matching the per-project counts exactly), then imported that one file into the JUnit view.

Also confirmed: Eclipse's JUnit view literally offers JUnit 6 as a test-runner kind (alongside 3/4/5) — this build's Jupiter jars are versioned 6.1.3, so "the Eclipse default plugin for JUnit6" in this environment means exactly that dropdown entry. Getting a plain @Test class to run live under that runner needed two jars beyond the junit-jupiter-api/junit-platform-commons pair this codebase already compiles against: junit-platform-engine and junit-platform-launcher (both 6.1.3, from Maven Central). That is a fact about wiring a throwaway Eclipse project, not about the change below — the Import route this page ships does not need them at all.

How to apply it

  1. Already in FearlessLang/Coordinator upstream main as of pull request #94 (merged, builds on #90) — nothing to apply on a current checkout. Building from an older commit instead? Apply eclipse-junit-xml-reports.patch from the zip below by hand: git apply eclipse-junit-xml-reports.patch from inside Coordinator/.
  2. Rebuild and run tests exactly as you already do — the console-launcher script, or Eclipse's own Run As > JUnit Test. One file appears: Coordinator/.out/junit_xml/all_auto_tests.xml, holding a <testsuite> block for every project that produced one.
  3. In Eclipse: Window > Show View > Other… > Java > JUnit if the view is not already open.
  4. Click the small ▼ dropdown next to the clock-with-arrow ("Test Run History") icon in the JUnit view's toolbar, choose Import…, and pick all_auto_tests.xml. Next time you add a project with Fearless-level tests, it just shows up in this same file — nothing new to pick.
  5. Browse the imported run like any other: expand nodes, click a red one to see its Failure Trace.

Prefer not to touch Coordinator at all yet, or want this for a Fearless project that is not one of the built-in integration tests? The zip also has a small, dependency-free, single-file Java program that does the same conversion standalone, merging into the same accumulating file across separate runs (rerunning a project replaces just that project's block): 

java FearlessJUnitXml.java <fearlessProjectRoot> [suiteName] [outDir]
# example
java FearlessJUnitXml.java C:\myFearlessProject myProject
# -> C:\myFearlessProject\.out\junit_xml\all_auto_tests.xml

The compromise, plainly

What you get
  • Every individual Fearless-level check as its own real, named, pass/fail/skip node in Eclipse's stock JUnit view — no plugin install, no custom Eclipse fragment, nothing beyond a feature Eclipse already ships.
  • Full failure detail (expected/actual/stack trace) exactly as Fearless produced it, browsable the same way as any other JUnit failure.
  • Zero changes to StandardLibrary or the Fearless language itself — the format it already produces was already this close to standard JUnit XML.
  • Generated automatically as part of the run you already do, in both the two flows this codebase already supports (script or Eclipse).
  • One file to Import…, regardless of how many projects report — today's four or a fifth added next month, with no list of project names to maintain anywhere.
What you don't get
  • A single seamless live view. Running "all tests" and seeing the granular results is two actions, not one — run, then Import…. Eclipse has no stock way to stream an externally-produced report into a launch's live tree.
  • Jump-to-source from an imported node. These are .fear files, not .java — Eclipse correctly reports "Test class not found in selected project" on double-click. No worse than today's plain console output, just not better either.
  • Coverage of Fearless projects that don't use base.UnitTests at all — nothing to report for those, so nothing is written (not a bug, there is genuinely no test data).
  • A file that reflects anything other than the most recent run of each project — that project's block is replaced wholesale next time it runs, not merged check-by-check.

The more ambitious version of this — a real custom org.junit.platform.engine.TestEngine that Eclipse's JUnit 5/6 launch support would discover on its own, giving one seamless live run with no import step — is possible in principle. It needs Fearless's test runner to separate "list the tests" from "run the tests," which it does not do today (the plan and the results are produced by the same pass). That is a real, larger change to the test framework itself, not attempted here.
