DEFECT 1 - divider cannot reach the icon-grid-only position
Dragging the split divider toward the right edge stopped at ~60% of
the window width, in both a default-size and a maximized (1920px)
window - verified with three separate drag attempts targeting
progressively further points, all landing at the same clamped
position. Root cause: FolderInfo's root panel had no minimum-size
override, so BorderLayout sized it to its widest content (the full
project path label), and JSplitPane won't shrink a panel past its
minimum size. Fix: root.setMinimumSize(new Dimension(0,0)) in
FolderInfo.java. Reverified: divider now reaches within a few pixels
of the window edge in both default and maximized windows; the icon
grid stays clickable at that width.

DEFECT 2 - Output area too small to read a 5-main run without scrolling
At the default window size, the Output area showed only its first
line; the header, buttons, Information and Mains-to-run sections above
it took nearly all the vertical space. Fix: default window height
raised from 620 to 900 (ManagerGui.java), capped against
GraphicsEnvironment.getMaximumWindowBounds() so the window can't land
partly off-screen on a shorter display. Reverified: window now fits
fully on screen and shows materially more output. Not fully fixed:
on this test machine (1920x1080 @150%) a 5-main compile+run still
needs one scroll to see the top of the log, since Information and
Mains-to-run (already collapsible, but expanded by default) still
claim a lot of the fixed space above Output. A further fix - e.g.
defaulting one of those sections to collapsed, or a resizable internal
splitter above Output - would close this the rest of the way but is a
more opinionated UX call, left for review rather than bundled in here.
